# 3.1 快速中继回退

后端构建版本：`2.6.4-civ6.1`，基于 EasyTier 2.6.4、提交 `8428a89d2dabc94c97d370ec607c6ca142473626` 的公开补丁。最终构建保留 `tun,aes-gcm,zstd` 功能；Zstd 用于兼容原版路由 RPC，游戏包压缩仍为默认关闭。

## 运行行为

- 玩家之间的已认证直连每 250ms 发送小型探测。单次响应门槛取最近平均 RTT 的 4 倍，最低 500ms、最高 2 秒。
- 首个探测超时即将该连接标记为疑似失效。后续数据直接使用已连接且已认证的管理员中继，不等待旧节点清理或 OSPF 路由失效。
- 旧连接继续探测；连续两个较新的探测成功，才恢复直连。迟到的旧探测结果不能覆盖较新的状态。持续无响应的旧连接随后按生命周期规则清理。
- 端到端会话和序号空间在切换时复用，不等待重新握手。没有对已经发出的游戏 UDP 包新增重传，也没有长期双路复制数据；网络复制相同密文包时，现有防重放窗口拒绝重复交付。
- 快速检测仅用于禁止代转数据的凭据客户端之间。服务器协调连接保留原有探测策略，玩家间小探测主要在 P2P 路径运行。
- 每包选路使用原子健康标记和缓存中继的常数次查找，不调用 PowerShell、不启动额外进程、不计算游戏包内容哈希。
- 桌面仍每 5 秒刷新显示；刷新频率不控制实际数据路径。程序只有私有游戏网段路由，默认路由和 DNS 行为保持不变。

这里的“立即”指检测结果产生后，下一个发包直接选择中继。断路发生到探测超时仍需时间，网络传输、发包频率与负载也会影响观察到的恢复时间。

## 构建和源码

上游源码、Cargo.lock 和许可证位于 `vendor/easytier/licenses/EasyTier-2.6.4-source.tar.gz`，补丁为 `build/easytier-fast-failover.patch`。构建脚本 `scripts/build-mesh-fork.py` 将同一补丁用于 Linux 静态 musl 和 Windows MSVC 两个平台；仅保留 `tun,aes-gcm,zstd` 功能。

```bash
python3 scripts/build-mesh-fork.py
```

交叉构建工具使用 [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild) 和 [cargo-xwin](https://github.com/rust-cross/cargo-xwin)。下载依赖仍由 Cargo.lock、固定编译器版本与校验值约束。

## 网络验证场景

六个独立 NAT、15 对玩家和 1Mbps 模拟中继出口，持续测量游戏端口 UDP 的 RTT 与丢包：

1. 全部直连。
2. 只将 1↔2 的直连延迟升高，保持通路可达，观察提前中继及恢复。
3. 将部分外层 UDP 包复制两份，统计接收端游戏套接字是否出现重复。
4. 三对直连完全阻断、全体直连阻断，以及恢复。

另保留原有双端认证、撤销、广播和 ACL 测试。Linux 网络验证不能代替 Windows 驱动和六人文明6真实对局。

## 2026-10-30 最终构建实测

以下为真实二进制、虚拟网卡、独立 NAT 命名空间下的合成 UDP 测量，没有启动文明6。
直连 RTT 模型为 80ms，中继模型为 120ms 加 1Mbps 出口的串行发送时间。

| 场景 | 实际结果 |
| --- | --- |
| 30 个方向全直连 | 959/959 次往返成功；RTT 中位 81.64ms，P95 86.12ms |
| 1↔2 可达但延迟升高 | 自动先中继；全体 1200/1200、受影响两方向 80/80 成功；旧路径在途包最大约 736ms |
| 外层 UDP 100% 复制 | 479/479 次往返成功；游戏套接字重复交付为 0 |
| 三对直连阻断 | 6 个方向断路至收发恢复 0.757–1.044 秒；20 秒内受影响探测丢 20/600；其他方向 2400/2400 成功 |
| 再阻断其余直连 | 新受影响 24 个方向恢复 0.786–0.989 秒；全体 20 秒内丢 84/3000 次探测 |
| 全部稳定中继 | 959/959 成功；RTT 中位 133.99ms，P95 140.30ms；服务器出口约 441kbps |
| 解除阻断 | 70 秒中 4199/4199 成功；约 15.4 秒时观察到全部恢复直连，期间保持中继收发 |
| 恢复后稳定直连 | 959/959 成功；RTT 中位 83.12ms，P95 86.45ms |

整个测试中六个游戏套接字合计收到 16098 次请求，重复交付为 0。程序没有新增游戏包重发：
“重复为 0”指测试中的相同外层密文复制被既有防重放机制拦截，不代表任意两份不同序号的相同游戏数据都会去重。
切换阶段仍会丢失已经送往断路路径的 UDP 包，不能承诺零丢包或游戏绝不掉线。

这里的恢复时间来自每方向真实 UDP 请求/响应的时间戳，包含探测、选路和传输。
路由状态的采样约每 2 秒一次，采样记录中约 3 秒的“路由全切换时间”不能当作数据恢复时间。
老连接长时间无响应而被清理后，恢复 P2P 仍需原生重新打洞；这不阻止中继继续收发。

原始汇总含每方向恢复时间、路径、丢包和套接字计数：[最终模拟结果](fast-failover-simulation.json)。
改动前约 11.5–23.3 秒恢复的记录保留在 [3.0 六人基线](six-player-test.md)。

## 原版服务器互通复核

六个最终新版客户端通过现有原版服务器的 UDP 入口，强制关闭 P2P，确认 15 对玩家、30 个方向都经服务器。
稳定阶段 719/719 次往返成功，RTT 中位 74.26ms、P95 90.15ms；冷启动阶段丢 3/179 次。
临时凭据随后全部撤销，服务器只保留原有两名玩家。
详细结果：[新版客户端与原版服务器互通](fast-failover-wan-compat.json)。

这一公网结果来自六个共享同一公网出口的容器，不能代表六条不同运营商线路，也不能推算固定游戏人数。
最终双端测试还通过了认证、撤销、未签发凭据拒绝、广播、TCP 隔离和默认路由不变。
PowerShell/C# 编译与升级兼容检查通过；Windows PE 已生成，真实 Windows 驱动、GUI 和文明6完整对局仍需实际电脑验证。

## 复现最终快速回退测试

先运行 `scripts/build-mesh-fork.py`，并按 validation.md 生成 `.build/client-test.toml`。
在包含 iproute2、iptables、tc 和真实 TUN 的一次性特权 Linux 容器中，以 `/workspace` 挂载项目，执行：

```bash
MESH_TEST_BIN=/workspace/.build/mesh-fork-out MESH_TEST_FAST=1 \
python3 -u tests/six_player_network.py /workspace/.build/fast-failover-final-simulation.json
```

使用新客户端前先断开旧客户端，再完整解压新版个人包；昵称、服务器 IP 和端口仍由玩家自行填写。
