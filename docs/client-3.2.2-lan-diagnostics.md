# 3.2.2 局域网房间发现诊断

日期：2026-10-30。增加局域网房间发现诊断，用于分析双向发现结果不一致的情况。诊断提供广播计数、游戏监听和防火墙信息，具体故障点需结合双方的采样结果定位。

## 网络诊断按钮

- 沿用实际玩家路由和虚拟 IP，并显示诊断版本和采样时间。
- 使用同一实例的本机 CLI `stats` RPC，只读取四个广播计数。没有读取或回显 `node info`、私钥、接入配置、统计标签、完整游戏安装路径。
- 显示 Windows 上文明6进程对应的 UDP 监听地址和端口，帮助检查通配、物理或虚拟地址绑定；不把绑定地址直接当成失败原因。
- 查询有效防火墙配置，以及文明6程序的已启用入站规则摘要。只读查询，不关闭防火墙、不改网络类别、不重置或修改规则。
- 单个查询失败时保留其他诊断。错误摘要不回显系统异常正文。
- 这些查询由“网络诊断”按钮触发；玩家列表每 5 秒读取一次路由。

## 广播计数的边界

四个计数名称为 `udp_broadcast_relay_packets_captured`、`ignored`、`forwarded`、`forward_failed`（后三项具有相同前缀）。这些是当前后端进程中广播捕获组件的累计统计，覆盖全部应用的 UDP 捕获候选及筛选/发送结果；尤其 raw socket 后端的捕获项可包含后续被筛掉的非物理源候选。

计数只在捕获 socket 成功打开后注册。计数缺失不能按零处理，也不能直接证明驱动损坏；存在也不证明捕获线程现在仍工作。当前 CLI 不能读取捕获后端或完整启动事件，所以界面不会虚构 WinDivert 启动状态。

转发成功只表示内部发送调用返回成功，不表示远端虚拟网卡或文明6已收到。游戏直接从虚拟网卡发出的广播不会经过物理捕获计数。需要结合前后两次采样、实际游戏监听地址与房间结果判断。

## 收集方法

双方完整解压同一个新版 ZIP，保留已有本机设置，连接后启动文明6。

1. 双方保持游戏运行，各点击一次联机助手的“网络诊断”，复制结果。
2. 朋友创建“多人游戏 → 局域网”房间，另一人在游戏中刷新数次。
3. 双方再次点击“网络诊断”，复制结果并标明房主/加入者和前后顺序。

计数变化、规则和监听信息可用于逐步定位问题。单侧数据不足以确认具体故障点，Windows 防火墙匹配、广播捕获和文明6房间发现需结合实际游戏结果判断。

## 验证

除原有服务端、通用客户端、状态 RPC 和驱动检查回归外，定向测试为 `tests/client-lan-diagnostics.Tests.ps1`。使用 Linux PowerShell 7.5 容器测试真实后端 stats RPC，Windows 游戏监听和策略查询使用模拟 cmdlet；这不是 Windows 内核或文明6实机测试。

本次执行结果：服务端 8 项单元测试、通用客户端回归、真实三节点状态 RPC 回归通过。新增诊断回归的四组检查全部通过，包括真实 stats RPC、PowerShell 5.1 数组输出语义模拟、有效策略来源读取、游戏进程/端点过滤、损坏配置的脱敏和只读行为。未运行 Windows 内核或文明6游戏实例。
